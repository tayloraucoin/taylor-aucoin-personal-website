# REV — Technical decisions (append-only)

Mason's record for the client design-review epic. One entry per real alternative weighed. Inherits M-INT (`docs/intake/specs/TECHNICAL-DECISIONS.md`); amendments to those are recorded here and cross-referenced there. Format: fast-lane ADR (context · options · decision · consequences · revisit trigger). IDs `M-REV-n` are citable from tickets.

## 2026-09-22 · REV-1 · M-REV-1 · One bearer key per review round, sha-256 hashed, minted by a local CLI and shown once

**Context:** A client site's server has to prove which round it is reporting into. There is no admin surface, no client account, and no shared secret between the two codebases yet. The engagement link already solved the same problem for the intake: a credential minted locally, stored only as a hash (M-INT-5, M-INT-6).
**Options weighed:** A) One global ingest secret for every client site, with the round named in the body. B) A key per client site, rounds named in the body. C) A key per round, minted by `yarn review:create`, stored as a sha-256 hash; the key *is* the round.
**Decision:** C. Under A, one leak is every client's data and the body's `roundId` is a claim the caller makes about itself. Under B the round is still a claim. Under C the credential names the round, so a handler has nothing to trust in the body about *where* a write goes — only *what* it is. Rotation is minting a new round, which is also the simplest possible admin story.
**Consequences:** `review_rounds.key_hash` unique; `requireReviewRound(key)` is the only reader by key and `resolveRoundFromRequest` the only header parser; the `ReviewRound` domain type omits the hash structurally. The plaintext exists only in the terminal that minted it. A lost key is a new round — there is deliberately no way to read one back, and no admin route mints them.
**Revisit trigger:** An admin surface that needs to mint or rotate keys without a terminal, which would move the minting behind `requireAdmin` but leave the hash-only storage.

## 2026-09-22 · REV-1 · M-REV-2 · Ids are the client site's, so retries are idempotent by primary key

**Context:** The client site waits eight seconds, treats a slow call as failed, keeps the write in the reviewer's browser, and retries. A lost *response* is indistinguishable from a lost *request* on that side, so any write may arrive twice.
**Options weighed:** A) Server-generated ids with a de-duplication heuristic (same round, same path, same body within a window). B) A client-supplied idempotency key header stored beside a server id. C) The client site generates the uuid and it is the primary key; every insert is `onConflictDoNothing` on it, every delete is scoped and tolerant of "nothing to do".
**Decision:** C. A is a guess dressed as a guarantee — two genuinely different comments with the same text are a real case. B is C with an extra column and an extra lookup. Under C the primary key constraint is the idempotency, and `returning()` yielding no row is the signal that this arrival was a retry — which is exactly the fact the submission's side effects need (M-REV-4).
**Consequences:** `review_comments.id` and `review_submissions.id` carry no `defaultRandom`. A retry of a delete after the row is already deleted, or with an id from another round, answers `{ ok: true }` and changes nothing. The contract's "every write must be idempotent on `id`" is met by schema, not by code that has to remember to check.
**Revisit trigger:** A write that cannot carry a client id — none exists in the contract today.

## 2026-09-22 · REV-1 · M-REV-3 · Route handlers, not server actions, because the caller is another site's server

**Context:** M-INT-2 chose server actions for client-initiated writes and route handlers for webhooks, cron, and upload issuance — "any second client of this data" was its own revisit trigger. The review layer is that second client: a Next.js server in a different repository, calling over HTTP with a bearer header.
**Options weighed:** A) Server actions, with the client site importing nothing and posting to the action's endpoint by hand. B) tRPC, as CC would for a second consumer. C) Plain route handlers under `app/api/review/`, JSON in and out, statuses and bodies fixed by the contract document.
**Decision:** C. A is a server action called from outside the app's action boundary — an encoding that is Next's private business and can change under a minor version. B is a typed contract for one consumer that will not share a package with this repo, at the cost of a dependency and a router. C is the shape `app/api/intake/upload` and the Stripe webhook already use, and the contract file is the type contract, held to on both sides by `satisfies` against hand-written shapes.
**Consequences:** Handlers stay thin — resolve, validate, call, reply — or this rots into a second service layer. Wrong-method replies are exported explicitly because the contract fixes their body. `force-dynamic` on each, since every reply depends on the header.
**Revisit trigger:** A third consumer, or a browser caller, either of which would want a shared package for the shapes and would reopen B.

## 2026-09-22 · REV-1 · M-REV-4 · The first submission stamps the round and emails Taylor through `notifyOps`; there is no admin surface

**Context:** Taylor needs to know a client has finished reviewing, and what they said, without a page to look at. The ops-notification rail (`notifyOps`, Resend to `INTAKE_NOTIFY_EMAIL`) already carries deposit and invoice events to the same inbox.
**Options weighed:** A) An admin page listing rounds and submissions, no email. B) Email on every submission POST. C) Email once, from the service, only when the submission insert actually lands; the retry path sends nothing.
**Decision:** C. A is a surface the contract §6 explicitly defers, and it would delay the first client round for a page Taylor would read once. B doubles up on every retry the client site makes — the reminder sweep learned that lesson (M-INT-9's send-once posture). C ties the side effect to the same fact that makes the write idempotent (M-REV-2): no returned row, no email.
**Consequences:** The three free-text answers travel in the email verbatim — it is Taylor's own inbox and reading them is the point — and nowhere else: not in a log line, not in a response. A failed send keeps the row and logs the round id; the record is the table, the email is the courtesy. `review_rounds.submitted_at` is `coalesce`d so a second distinct submission (a new id) does not move the stamp.
**Revisit trigger:** The admin build for this epic, which would add the page and may keep the email; or a second recipient, which would make the plain-text rail insufficient.

## 2026-09-22 · REV-2 · M-REV-5 · Submissions carry an optional, versioned `answers` list; the email prints it without knowing the questions

**Context:** The client site's feedback form (kryshan-film-portfolio KR-6) now asks rankings, 0.0–7.0 sliders and forks whose set changes per client. REV-1's `review_submissions.payload` is jsonb precisely so that a new question never needs a migration here (the schema file's own docstring), but the validator and the `notifyOps` summary knew only six fields.
**Options weighed:** A) A field per question here. That is a deploy of this repo for every client round. B) Records keyed by question id with a separate label map. C) An ordered array of self-describing items (`id`, `kind`, `section`, `label`, a value; options as `{ id, label }`; a scale's ends and intake `baseline`), as a union discriminated on `kind`, under `answers: { schema, items }`.
**Decision:** C, as the client site's M-KR-4. jsonb reorders object keys, so B would lose question order in the stored row; C keeps it, and each item reads without a join. The validator checks shape, bounds and unique ids, not question identity: this side cannot know a client's questions and must not try. `answers` is optional and nullable, so every pre-REV-2 body still validates. `notifyOps` prints each answered item in form order, grouped by section, and prints a scale's intake baseline beside the new value.
**Consequences:** No migration. The payload type grows an optional key; existing rows read as `answers` absent. The email body can grow by about twenty lines; still plain text on the same rail. Answer labels are client-authored text in Taylor's own inbox, never in a log line (M-REV-4's posture).
**Revisit trigger:** The admin surface for this epic (contract §6), which may want the question sets registered here to aggregate across rounds; or a question kind outside rank / scale / choice / text.

## 2026-09-22 · REV-4 · M-REV-6 · One shared sister-repo key; the client site names itself with a static `clientApp`; rounds are created on first contact (supersedes M-REV-1)

**Context:** M-REV-1 minted one bearer key per round with a local CLI, stored its hash, and let the key name the round. In practice that was one more command and one more concept per client for Taylor, who asked for the obvious shape: the client repo says which client it is, and a key proves it is one of his repos.
**Options weighed:** A) Keep M-REV-1. B) No key at all, identity only. C) One shared secret, `REVIEW_INGEST_KEY`, in this repo and every client site; the client site sends `X-Review-Client-App` (static slug), `X-Review-Engagement` (production engagement id) and `X-Review-Label`; the round is found or created by `client_app`.
**Decision:** C, on Taylor's call. B leaves a public endpoint that writes rows and sends email open to anyone. C keeps that gate at the cost M-REV-1 avoided: every holder of the key can post as any client. All holders are Taylor's own repos, so that is accepted. The engagement link is soft: linked when the id exists in this database (production), left null elsewhere, so local and staging runs work against an id that exists only in production.
**Consequences:** `review_rounds.key_hash` dropped and `client_app` (unique) added (migrations `0018`, `0019`). `yarn review:create`, `requireReviewRound`, `hashReviewKey`, `createReviewRound` and `createReviewRoundInput` removed. `REVIEW_INGEST_KEY` is a new untiered env var here; unset refuses every review request. The key is compared as sha-256 digests with `timingSafeEqual`. A round is never rewritten by a later request. Rotation means changing the key here and in every client site at once.
**Revisit trigger:** A client repo not controlled by Taylor, or a key leak that makes simultaneous rotation painful; either brings back per-client keys (M-REV-1's shape).
